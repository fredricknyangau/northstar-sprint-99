# Northstar Support Deflection MVP — go-live readiness (Issue #18)

**Decision: not ready to launch.** The codebase implements the two intended categories—**order status** and **returns & refunds**—on the FastAPI side. Order status can read an order by ID; return creation can create a pending record for an existing order; return status can read a return. Existing automated tests cover the order-status happy/not-found paths and support-classifier happy/fallback paths. The support classifier also distinguishes order and return queries.

The customer-facing MVP is not end-to-end: all three frontend controls generate hard-coded/local responses and contain no `fetch()` calls. A customer can therefore receive a “shipped” or “return created” result for any non-empty ID without the backend being called. Product availability is not implemented; it is only a classifier example. Live API execution was also not possible in this QA environment because dependencies could not be installed past a locked global package, so production checks remain required.

Before Northstar takes ownership, provision PostgreSQL; set `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD`; run migrations **001 through 004 in order**; then load `backend/app/database/seed.sql` (004 is required for seed/query columns). Install `backend/requirements.txt`, run the test suite from `backend`, and start FastAPI on port 8000. Serve `frontend/` over HTTP and configure its API base URL—after replacing mock logic with real calls. Monitor API 4xx/5xx rates, database connection failures, request latency, and return-creation volume; retain structured request IDs and alert on spikes. The backend owner should own API/database issues; the frontend owner should own integration and customer messages; Northstar should nominate a support/product owner for return-policy decisions.

Priority fixes: (1) connect each UI flow to the API with loading, empty/not-found, and network-error states; (2) add authentication/ownership authorization, restrict CORS, and rate-limit to prevent ID enumeration; (3) enforce return eligibility, non-blank reasons, and duplicate/refunded-order rules, returning `201` on creation; (4) replace `innerHTML`, add `aria-live` result announcements and stronger focus states; (5) add API integration/edge-case tests and run a production-like smoke test. There is no evidence of stack traces being intentionally returned, but verify production error responses before launch.
